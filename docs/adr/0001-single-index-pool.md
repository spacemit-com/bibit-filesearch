# ADR 0001：索引状态收归单一池子，执行路径收敛为一条

- 状态：已采纳
- 相关：[`../scan-status-contract.md`](../scan-status-contract.md)、`CONTEXT.md`

## 背景

索引有两条路径：

- **全盘扫描**（用户点「保存并索引」触发）：写库 `queued` → 写库 `vectorizing` → 算 → 写库 `completed`。
- **自动增量**（watcher 监听目录）：不写库，直接调 `Indexer.index_file()` → 算 → 写库 `completed`。

两条路径都能触发索引，但只有前者在库中留下中间态。于是：

1. 增量索引期间，正在算的文件在库中**不存在**，界面的「待向量化」只能靠一个**进程内整数**兜底；
2. 那个整数挂在两条路径的公共入口 `index_file()` 上，导致全盘扫描正在算的文件被**数了两遍**
   （库中 `vectorizing` 与进程内活跃路径指向同一文件的帧占 99.2%；「待向量化」稳定多算 1）；
3. 同一文件可能被两条路径各算一遍（端到端耗时接近翻倍）；
4. 数字与事实不符的其他表现：放入 N 个文件显示 1；排队中删除后计数长时间不降；
   三格合计小于知识库文件数。

## 决策

**索引状态只存一处（`files` 表即池子），索引只有一条执行路径（一个常驻消费者）。**

1. watcher 与全盘遍历降级为**生产者**：只往池子放文件、撤文件，不索引。
2. 新增常驻**消费者**：从池子取活、调执行器、把终态写回池子。
3. **一行的状态只由消费者写**；执行器只算不写状态。
4. 入池与唤醒分离，入池后必须唤醒。
5. 撤池要能取消**尚未被消费**的行；正在算的不打断，算完丢弃。
6. 对外计数以池行状态为准，进程内计数不再作为状态来源。

## 后果

**好的**：

- 状态有唯一真相，可跨进程、跨重启读到；「待向量化」= 池中未算完的行数，不再有重复计数。
- 两条路径收敛为一条，同一文件在池内天然只被算一次。
- 删除/移出排队文件时计数**立即**响应（从「等当前算完」变成「删掉就是删掉」）。
- 池外的两类文件（不可索引、遍历失败）可被统一出口表达，界面不再有看不见的文件。

**代价**：

- `Indexer` 的职责要重划（从「算并写状态」变成「只算」），`mark_failed` / `_upsert_meta_only` /
  三个调用方要跟着调整。
- 池子化会改变四个现有消费端的前提（进度分母 `total`、`skipped` 兜底、`_recover_interrupted`、
  `truncated_files`），需逐个复核。
- 消费者需要常驻（原实现在池空时退出线程），唤醒机制要处理丢失与竞态。
- 对外 JSON 要增删字段，插件需同步两版本过渡。

**不这样做会怎样**（保留现状的代价）：

- 每加一条新的索引触发路径（例如未来的定时扫描、外部 API 触发），都要重复解决一次
  「状态写不写库、计数怎么算」；重复计数与删除延迟会以新的形式重现。
- 界面无法自证「三格合计 = 知识库文件数」，用户会持续怀疑数字。
